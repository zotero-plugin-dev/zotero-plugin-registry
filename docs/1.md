
# 技术需求文档：Zotero Store Bot (`zbot`)

## 1. 项目与架构定义

### 1.1 项目定位

`zbot` 是 Zotero 插件商店 Monorepo 中的核心自动化工具。它负责读取静态元数据、抓取远程更新信息、合并补丁数据、下载校验 XPI 包，并生成供前端使用的标准化 JSON 文件。

### 1.2 架构上下文

* **Monorepo 结构**:
* `bot`: 本文档描述的 CLI 工具。
* `shared`: 存放 `types.ts` 和 `meta.schema.json`，是数据协议的唯一真理来源 (Single Source of Truth)。
* `plugins`: 数据源目录，结构为 `plugins/<plugin-id>/meta.json`。
* `frontend`: 展示层。

* **依赖约束**:
* **Runtime**: Node.js (ESM), `tsx` 运行。
* **HTTP**: `axios` (需配置 GitHub Token 避免限流)。
* **GitHub API**: `@octokit/rest` (用于获取 Stars/Forks/Release info)。
* **File System**: `fs-extra`, `globby`。
* **Utility**: `es-toolkit`, `adm-zip` (解析 XPI)。
* **Validation**: `ajv` 或 `zod` (基于 Schema)。
* **Git**: `simple-git`。

## 2. 数据模型与协议

### 2.1 输入：`meta.json` (Source)

位于 `plugins/<plugin-id>/meta.json`，由开发者或社区维护。
需支持以下字段（需同步更新 `shared/types.ts`）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | **(必填)** 插件唯一 ID，必须与目录名一致 (e.g., `zotero-format-metadata@northword.cn`)。 |
| `name` | string | 显示名称。 |
| `repoUrl` | string | **(可选)** 源代码仓库地址 (GitHub/Gitee)。 |
| `updateUrl` | string | **(必填)** Zotero 标准 `update.json` 地址。 |
| `tags` | enum[] | 必须在允许列表内：`metadata`, `interface`, `ai`, `writing` 等 (参考 Copilot 总结)。 |
| `patchedVersions` | array | 手动维护的版本列表，用于补丁。格式同 Zotero Update Manifest。 |
| `description` | string | 简短描述。 |

### 2.2 输出：构建产物 (Artifacts)

Bot 运行后，应在每个插件目录下生成以下文件（不应提交到 git，但在 CI 中会部署）：

1. **`meta.generated.json`**: 包含合并后的完整信息（Base Info + All Versions + Repo Stats + Download Stats）。
2. **`latest.json`**: 仅包含最新版本的精简信息，供快速索引。

## 3. Bot 核心处理流程 (Pipeline)

CLI 入口应支持 `zbot build` (全量) 和 `zbot build --only <id>` (单量)。

### 3.1 初始化与发现

1. 加载 `shared/types.ts` 定义的 Schema。
2. 根据 CLI 参数扫描 `plugins/` 目录。
3. **缓存加载**: 读取 `.cache.json` (记录 URL 的 ETag/Last-Modified/Hash)。

### 3.2 单个插件处理逻辑 (Processor)

对每个插件执行以下步骤，**单个失败不应中断整个进程**：

#### Step 1: 静态校验

* 读取 `meta.json`。
* 校验 `id` 是否与目录名匹配。
* 校验 `tags` 是否在枚举范围内。
* 校验 JSON 格式是否符合 Schema。

#### Step 2: 获取远程版本 (Remote Fetch)

* **如果有 `updateUrl`**:
* 发送 GET 请求（带缓存头）。
* 解析返回的 JSON (Zotero Manifest Format)。
* 提取 `addons[id].updates` 数组。

* **如果有 `repoUrl` (GitHub)**:
* 调用 GitHub API 获取 Repo 信息 (Stars, Forks, Description, Last Push)。

#### Step 3: 版本合并 (Version Merging - 核心需求)

* **场景**: 远程 `update.json` 只有 v2 (Zotero 7)，但 `meta.json` 的 `patchedVersions` 字段手动补全了 v1 (Zotero 6)。
* **逻辑**:

1. 初始化 `versionList` = 远程获取的 updates 列表。
2. 读取 `meta.json` 中的 `patchedVersions` 列表。
3. **合并策略**: 以 `version` 号为 Key。

* 如果远程列表里没有该版本，则**追加**手动版本。
* 如果远程列表里已有该版本，以**手动配置为准** (允许手动修正远程错误的下载链接)。

1. **排序**: 按版本号语义化排序 (SemVer)。

#### Step 4: 资产验证 (XPI Validation)

* 对 `versionList` 中的最新版本（或所有版本，取决于策略配置）：
* 检查下载链接 (`updateLink`) 是否在缓存中。
* 下载 XPI 文件（Stream 下载，限制大小）。
* 使用 `adm-zip` 读取 XPI 内的 `manifest.json` 或 `install.rdf`。
* **验证**: 确认 XPI 内的 ID 与 `meta.json` 的 ID 一致。
* **提取**: 提取图标 (icon.png/svg) 并保存到插件目录（如果目录内没有手动放置 icon）。

#### Step 5: 生成产物

* 构造 `meta.generated.json`:

```json
{
  "pluginId": "...",
  "stats": { "stars": 120, "downloads": 5000 },
  "versions": [ ... merged versions ... ],
  "latestVersion": "2.0.0",
  "compatibleApps": { "zotero": { "min": "6.0", "max": "7.0" } }
}

```

* 写入文件系统。

### 3.3 错误处理 (Error Handling)

* 使用 `ProcessResult` 接口收集状态：

```typescript
interface ProcessResult {
  pluginId: string;
  status: 'success' | 'error' | 'skipped';
  error?: {
    stage: 'schema' | 'fetch' | 'xpi' | 'merge';
    message: string;
  }
}

```

* **本地开发**: 遇到 Error 直接红色高亮打印。
* **CI 环境**: 收集所有 Error，最后统一通过 exit code 1 退出。

## 4. GitHub Actions 集成需求

Bot 需包含专门的模块 (`src/report.ts`) 处理 CI 交互。

### 4.1 PR 模式 (`zbot check`)

* **触发**: Pull Request 事件。
* **逻辑**:

1. 利用 `simple-git` 对比 `origin/main`，找出变动的 `plugins/<id>`。
2. 仅对变动插件运行 Processor。
3. **Schema 验证**: 必须通过。
4. **链接验证**: `updateUrl` 和 `repoUrl` 必须可访问 (HTTP 200)。
5. **Schema 兼容性**: 确保手动补丁 (`patchedVersions`) 格式正确。

* **输出**:
* 如果失败，通过 GitHub API 在 PR 下发表评论，列出具体错误。
* CI Job 标记为失败。

### 4.2 生产构建模式 (`zbot build`)

* **触发**: Schedule (每日) 或 Push to Main。
* **逻辑**:

1. 全量运行。
2. **Issue 报告**:

* 汇总所有失败的插件。
* 检查是否已存在当天的报告 Issue。
* 创建/更新 Issue: "Plugin Sync Report [Date]"，@相关维护者。

1. **部署**:

* 将生成的 json 文件推送到 `publish` 分支（或构建产物目录）。

## 5. 开发规范

### 5.1 代码风格

* **Linting**: 严格遵守 `@antfu/eslint-config`。
* **Type Safety**: 禁止 `any`，所有外部数据（如 Fetch 返回的 JSON）必须经过类型断言或 Zod 校验。

### 5.2 目录结构 (Bot 内部)

```text
bot/
├── src/
│   ├── cli.ts          # 命令行入口 (Commander)
│   ├── processor.ts    # 单个插件处理流 (Fetch -> Merge -> Write)
│   ├── loaders/        # 负责读取 meta.json 和 update.json
│   ├── merger.ts       # 负责版本合并逻辑
│   ├── report.ts       # GitHub Issue/PR 交互
│   ├── utils/
│   │   ├── http.ts     # Axios 封装 (Auth + Timeout)
│   │   ├── git.ts      # 变更检测
│   │   └── xpi.ts      # Zip 解析
│   └── types.ts        # Bot 内部类型 (继承自 Shared)

```

### 5.3 缓存策略

* 文件: `.cache/http-cache.json`
* Key: 请求 URL。
* Value: `{ etag: string, lastModified: string, data: any, timestamp: number }`
* GitHub Actions 中利用 `actions/cache` 挂载此目录。

## 6. 任务清单 (AI Agent Instructions)

请按以下顺序实现：

1. **Shared Setup**: 完善 `shared/src/types.ts`，增加 `patchedVersions` 字段定义，并生成 `meta.schema.json`。
2. **Loader & Merger**: 实现读取 `meta.json` 和远程 `update.json` 的逻辑，编写单元测试验证“手动版本覆盖/追加”逻辑的正确性。
3. **Processor Core**: 串联 HTTP 请求、XPI 下载、图标提取逻辑。
4. **CLI Wrapper**: 使用 Commander 封装 `build` 和 `check` 命令。
5. **GitHub Reporter**: 实现 PR 评论和 Issue 创建功能。
